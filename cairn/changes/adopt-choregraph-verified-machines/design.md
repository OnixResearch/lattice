## Context

Lattice has active changes to adopt immutable Radicle sources for execution-graph and Nickel evaluation. Those changes establish the behavior and evaluator baselines needed for a controlled Choregraph migration.

## Success Contract

Completion requires accepted prerequisites, exact Choregraph evidence, complete call-site inventory, dual-run parity, persisted-state compatibility, one production transition path, and tested rollback. Adding Choregraph beside the current path or calling its CLI as an unbounded subprocess is false completion.

## Prerequisites

The local execution-graph and Nickel evaluator adoption changes must complete first. Choregraph must then provide an immutable source, AGPL-compatible license, source archive, release bundle, single-step and trace proof results, trusted-surface manifest, Kamacite artifacts, restricted Nickel boundary, and Lattice conformance evidence.

Upstream evidence proves linkage only. Lattice runs its own integration and runtime checks.

## Authoring and Lowering Boundary

Lattice retains configuration discovery, source roots, imports, product contracts, evaluator selection, fallback policy, safe diagnostics, and typed workflow decoding.

The selected evaluator produces an in-memory value and bounded source receipt. Lattice passes that value to Choregraph's pure lowerer. The lowerer returns canonical IR or stable typed issues. It does not read Lattice files.

No evaluated output can bypass Choregraph admission or Lattice product validation.

## Machine Adapter

The adapter maps stable Lattice node, edge, state, event, and declared-effect data to Choregraph. Choregraph owns graph and transition decisions. Lattice owns values, typed ports, runtime keys, credentials, cache policy, retry policy, schedules, triggers, budgets, approvals, persistence, and UI events.

The adapter contains no independent cycle, ordering, readiness, lifecycle, resume, replay, or transition algorithm.

## Persisted Compatibility

Migration fixtures cover existing pending, ready, running, completed, failed, and cancelled states plus stored event sequences. Each mapping binds the workflow revision, old schema, new schema, and machine identity.

Unsupported, partial, foreign, stale, or ambiguous records fail closed. Replay computes state only and never emits a fresh runtime dispatch.

## Dual-Run and Cutover

Temporary tests compare admission diagnostics, order, dependencies, groups, readiness, lifecycle, terminal rejection, resume, replay state, and effect-intent shape.

Production remains on the old path until every required case passes. Cutover then selects Choregraph only and removes temporary dual-run and duplicate decision code.

## Source and Rollback

Cargo and Nix select one exact Choregraph revision. No GitHub, floating, sibling, vendor, or runtime fallback is allowed. Lockfiles are generated by owning tools, and `flake.lock` is never edited manually.

Rollback is one reviewed VCS operation that restores source declarations, generated locks, adapters, and persisted compatibility behavior.

## Claim Boundary

Lattice may state that it consumes an exact Choregraph source with named proof evidence. It must not state that Choregraph proves Lattice runtime, persistence, authorization, effects, UI, external services, or release readiness.
