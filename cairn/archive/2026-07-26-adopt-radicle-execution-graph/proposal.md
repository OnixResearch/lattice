## Why

Lattice uses a provenance-recorded vendored copy of Seaglass's execution-graph core because no admitted external source existed during the original adoption. The standalone `execution-graph` repository now has the right product-neutral boundary, but consumer cutover must wait for its Radicle publication, exact source receipt, and compatibility evidence.

Lattice should replace the vendor snapshot only through one immutable Radicle-backed revision. GitHub, a floating branch, and an ambient sibling path must not become fallback sources.

## What Changes

- Baseline the current vendored source, sync provenance, graph adapter, positive and negative tests, Cargo source, and Nix source identity.
- Verify the standalone Radicle publication receipt, canonical RID, exact Git object, license, and source archive before changing dependencies.
- Alias `execution-graph-core` only where needed to preserve current Rust imports during migration.
- Align Cargo and Nix on the same Radicle HTTPS adapter and exact revision; generate lock changes only with Cargo and Nix.
- Dual-run vendor and external graph decisions across admission, ordering, readiness, lifecycle, resume, critical path, and bottleneck fixtures.
- Remove vendored copies and sync tooling only after parity, repository checks, and rollback review pass.

## Success Criteria

- The exact external source is available from the admitted Radicle path with no GitHub or sibling fallback.
- All current positive and negative graph behavior remains compatible.
- Lattice retains runtime, scheduler, values, ports, policies, events, persistence, artifacts, and evidence authority.
- Cargo, Nix, documentation, and source receipts name the same RID adapter and Git revision.
- A VCS rollback can restore the previous vendor source and lock state without hidden acquisition fallback.

## Non-Goals

- Changing graph semantics, node types, scheduler behavior, retries, or execution policy.
- Moving product runtime or evidence authority into `execution-graph-core`.
- Claiming publication or parity proves workflow correctness or release readiness.
- Publishing or pushing the external repository from this consumer change.

## Impact

- **Dependencies**: `Cargo.toml`, Cargo lock, Nix source declarations and lock generated by owning tools.
- **Source**: runner adapter and vendor/sync paths only as required for cutover.
- **Testing**: exact-source checks, dual-run conformance, repository validation, Octet, Cairn, and Nix.
