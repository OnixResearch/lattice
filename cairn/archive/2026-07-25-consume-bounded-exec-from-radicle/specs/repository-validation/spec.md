# Repository Validation Delta

## ADDED Requirements

### Requirement: Canonical Radicle Bounded Exec source
r[lattice.repository_validation.radicle_bounded_exec_source] Lattice MUST acquire Bounded Exec from the accepted Radicle repository identity through an admitted HTTPS Git endpoint and MUST retain the exact reviewed dependency revision during the forge pilot.

#### Scenario: Cargo and Nix acquire the accepted source
r[lattice.repository_validation.radicle_bounded_exec_source.scenario.accepted]
- GIVEN the verified Bounded Exec publication receipt names the canonical RID, admitted endpoint, and reviewed Git revision
- WHEN Cargo and Nix resolve the dependency
- THEN both paths MUST acquire that exact revision from the Radicle-backed source

#### Scenario: GitHub remains the Bounded Exec source
r[lattice.repository_validation.radicle_bounded_exec_source.scenario.github-rejected]
- GIVEN a current Cargo, Nix, Crane, or lock declaration still acquires Bounded Exec from GitHub
- WHEN source identity validation runs
- THEN Lattice MUST reject the pilot cutover before accepting a successful migration claim

### Requirement: Generated lock agreement
r[lattice.repository_validation.radicle_bounded_exec_locks] Lattice MUST keep Cargo, Nix, Crane source substitution, and generated lock identities aligned on the same accepted Bounded Exec endpoint and exact Git revision.

#### Scenario: Generated locks agree
r[lattice.repository_validation.radicle_bounded_exec_locks.scenario.aligned]
- GIVEN source declarations were updated and both lockfiles were regenerated by their owning tools
- WHEN the pure source-identity validator compares the declared and locked facts
- THEN it MUST report one accepted Bounded Exec source identity with no mismatch diagnostics

#### Scenario: Source identities drift
r[lattice.repository_validation.radicle_bounded_exec_locks.scenario.drift]
- GIVEN a RID, endpoint, revision, lock entry, Crane source string, crate set, or expected source identity differs
- WHEN source identity validation runs
- THEN it MUST fail with stable deterministic diagnostics before a successful repository-build claim is accepted

### Requirement: Radicle source availability evidence
r[lattice.repository_validation.radicle_bounded_exec_availability] Lattice MUST require BLAKE3-bound OnixOS evidence that every admitted seed path can provide the exact Bounded Exec object and that any single seed outage leaves an admitted acquisition path.

#### Scenario: One seed is unavailable
r[lattice.repository_validation.radicle_bounded_exec_availability.scenario.seed-outage]
- GIVEN accepted evidence records complete replication and one seed is stopped
- WHEN the dependency is acquired through the surviving configured path
- THEN the exact Bounded Exec object MUST remain available without consulting GitHub for that dependency

#### Scenario: Radicle paths are unavailable
r[lattice.repository_validation.radicle_bounded_exec_availability.scenario.no-fallback]
- GIVEN no admitted Radicle-backed path can provide the dependency
- WHEN Cargo or Nix attempts acquisition
- THEN acquisition MUST fail closed and MUST NOT silently retry a GitHub Bounded Exec source

### Requirement: Bounded-process behavior preservation
r[lattice.repository_validation.radicle_bounded_exec_behavior] Lattice MUST preserve its existing bounded local-process behavior and consumer-owned policy while changing only the Bounded Exec forge source and transport metadata.

#### Scenario: Existing bounded process matrix runs
r[lattice.repository_validation.radicle_bounded_exec_behavior.scenario.preserved]
- GIVEN the Radicle-backed source resolves to the same reviewed Bounded Exec revision
- WHEN focused success, failure, deadline, truncation, cancellation, and process-group teardown tests run
- THEN their existing policy classifications and product diagnostics MUST be retained

#### Scenario: Transport success is overclaimed
r[lattice.repository_validation.radicle_bounded_exec_behavior.scenario.non-claim]
- GIVEN Cargo and Nix successfully fetch and build the Radicle-backed dependency
- WHEN migration evidence is rendered
- THEN Lattice MUST NOT claim Radicle protocol correctness, Bounded Exec correctness, host sandboxing, third-party GitHub independence, or release readiness from that result
